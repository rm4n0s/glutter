# CLAUDE.md

Guidance for Claude Code when working in this repository (Go, hosted on GitHub).

## Project
Glutter is a cgo-free GUI toolkit for Go (Android, from 1.6, is the one exception) that reproduces Flutter's framework API (widgets, rendering, gestures, animation, Material 3) on its own engine: a Wayland/X11 platform layer, a Vulkan renderer with an OpenGL ES 3.0 fallback (system libraries called through purego), and text layout on go-text. Linux desktop comes first; 1.1 adds the web (`GOOS=js GOARCH=wasm`, WebGPU with a WebGL 2 fallback, standard Go only, no TinyGo); 1.6 adds Android (`GOOS=android`, an APK built by `cmd/glutter-android`, a small Java embedding, Vulkan with a GLES fallback; SPEC §24); 1.8 adds Windows (`GOOS=windows`, Win32 through the standard library's `syscall`, Direct3D 12 at feature level 11_0; SPEC §25), tested under Wine. Every OS- and GPU-specific piece sits behind internal interfaces so Windows, macOS and mobile can be added later.

**`docs/SPEC.md` is the source of truth.** Read the sections that cover a task before starting it. If the code and the spec disagree, or a task needs a decision the spec doesn't make, ask instead of guessing. When a decision changes, update the spec on the same branch.

## Commands
- Build: `go build ./...`. Glutter is cgo-free; `CGO_ENABLED=0 go build ./...` must always work
- Build modes (SPEC §12.9): a plain `go build`, `go run` or `go install` is a release build (`foundation.ReleaseMode`); `-tags debug_mode` makes a debug build (the asserts, the diagnostics and the `GLUTTER_DEV_*` hooks of the examples and the platforms), `-tags glutter_profile` a profile build. The tools (`glutter-web`, `glutter-android`, `glutter-windows`, `glutter-macos`, `glutter-ios`) build release builds unless given `-debug`; their `shot` builds a debug build unless given `-debug=false`
- Test all, in both modes: `go test -race ./...` (a release build) and `go test -race -tags debug_mode ./...` (a debug build) (the race detector needs cgo, so these need a C compiler). A test of debug-only behavior is in a file with `//go:build debug_mode` or skips when `foundation.DebugMode` is false
- Test the cgo-free path: `CGO_ENABLED=0 go test ./...`
- Test one package: `go test ./widgets -run TestName -v`
- Tests that need a real display/GPU: `go test -race -tags 'glutter_display debug_mode' ./...`
- The display tests under one X server (from step 32.2): `scripts/headless-x11.sh -- go test -p 1 -race -tags 'glutter_display debug_mode' ./internal/engine ./internal/platform/linux/x11 ./internal/gpu/shmwindow`; `-p 1` because the tests of the `x11` package change the `Xft.dpi` of the server, which every other client of it (the apps that the `engine` tests start) sees, and a run of the packages side by side failed once in about twenty.
- Web build and checks (from step 19.1): `GOOS=js GOARCH=wasm go build ./...`, `GOOS=js GOARCH=wasm go vet ./...`, `scripts/test-wasm.sh` and `scripts/test-wasm.sh -tags debug_mode` (unit tests under Node, in both modes)
- Tests in a headless browser: `go test -tags 'glutter_browser debug_mode' ./...` (SPEC §17)
- Run an example on the web: `go run ./cmd/glutter-web serve ./examples/counter`
- Android check (from step 25.1): `scripts/check-android.sh` (build and vet for android/arm64 and android/amd64 with the NDK; needs `ANDROID_HOME`)
- Tests on the Android emulator (from step 25.2): `go test -p 1 -tags 'glutter_android debug_mode' ./...` (SPEC §24.13; they start and stop the emulator themselves)
- Audio tests on Linux (from step 31.5): `scripts/headless-audio.sh -- go test -p 1 -tags glutter_audio ./internal/platform/linux/pulse ./internal/platform/linux/alsa` (a private PipeWire server with a null sink and source; `GLUTTER_AUDIO_SOAK=600` for the ten-minute run; SPEC §28.8); it never touches the sound of the machine
- Audio under Wine (from step 31.6): `scripts/headless-audio.sh -- env GOOS=windows CGO_ENABLED=0 go test -tags 'glutter_wine glutter_audio' -exec "$PWD/scripts/wine-exec.sh" -p 1 ./internal/platform/windows/wasapi` (`winepulse` to the same private server; the host-side test `wine_host_test.go` records the sink's monitor); audio on the Android emulator: `go test -p 1 -tags 'glutter_android debug_mode' -run TestAudio ./internal/androidtest` (the AVD `glutter-37-audio`, which has audio hardware; `examples/dev/android-audio` is its app); audio in Chromium: `go test -tags 'glutter_browser debug_mode' -run TestBrowserAudio ./internal/platform/web` (`internal/platform/web/audiotest`; Chromium only, SPEC §28.8)
- Sensors (from step 31.7): on the Android emulator `go test -p 1 -tags 'glutter_android debug_mode' -run TestSensors ./internal/androidtest` (it sets the virtual sensors with `adb emu sensor set`; `examples/dev/android-sensors` is its app); in Chromium and Firefox `go test -tags 'glutter_browser debug_mode' -run TestBrowserSensors ./internal/platform/web` (`internal/platform/web/sensortest`, which sends `DeviceMotionEvent`s to the page)
- Run an example on Android (from step 25.2): `go run ./cmd/glutter-android run ./examples/counter` (a connected phone or a running emulator)
- Windows build and checks (from step 28.1): `GOOS=windows GOARCH=amd64 go build ./...`, `GOOS=windows GOARCH=amd64 go vet ./...`, `GOOS=windows GOARCH=arm64 go build ./...`, `scripts/test-windows.sh` and `scripts/test-windows.sh -tags debug_mode` (the unit tests of the packages that build for Windows, under Wine, in both modes)
- Wine tests (from step 28.1): `GOOS=windows go test -tags 'glutter_wine debug_mode' -exec "$PWD/scripts/wine-exec.sh" -p 1 <packages>`; the host-side harness: `go test -tags 'glutter_wine debug_mode' -p 1 ./internal/winetest`
- Every example under Wine (from step 28.15): `go test -tags 'glutter_wine debug_mode' -p 1 -run TestEveryExampleDrawsItsFirstFrameUnderWine ./examples`; Windows performance: `scripts/perf-windows.sh -m` (Wine's numbers, vkd3d on lavapipe; one measurement at a time)
- Build a Windows `.exe` with its manifest and icon (from step 28.14): `go run ./cmd/glutter-windows build ./examples/counter`; run it under Wine: `go run ./cmd/glutter-windows run -headless ./examples/counter`; a proof screenshot: `go run ./cmd/glutter-windows shot -o out.png ./examples/counter`
- Run a Windows program under Wine, headless: `scripts/wine-exec.sh ./app.exe`; a screenshot of the X root: `scripts/wine-screenshot.sh out.png -- <command>`
- Update golden images: `go test ./... -run Golden -update-goldens`, then review every changed PNG
- Memory tests (from step 29.21): `go test -run Leaks ./material ./widgets ./gestures ./internal/gpu/... ./internal/platform/linux/wayland ./offscreen ./gpu ./audio`; `LEAKTEST_SCALE=5` for a longer soak, `LEAKTEST_REPORT=file` for the numbers, `LEAKTEST_PROFILE=dir` for heap profiles (SPEC §15, "Memory over time"). Memory leaks are a priority: a leak found is fixed, with a test that fails before the fix
- Vet: `go vet ./...`
- Lint: `golangci-lint run`
- Format: `gofmt -w .` (or `goimports -w .`)
- Generate (Wayland protocol bindings, key tables, material re-exports, shaders): `go generate ./...`; the gamepad tables of SDL 3 (`internal/gamepaddb/*_gen.go`): `go run ./cmd/glutter-gen gamepaddb` (it reads `reference/sdl`); the shaders need naga 30.0.1 (D20), and `glutter-gen shaders` also writes the HLSL, rewriting naga's sampler heap into plain registers. A shader never reads `instance_index` (SPEC §9.8)
- API conventions check (SPEC §12.13): `go run ./cmd/glutter-gen apicheck -allow cmd/glutter-gen/apicheck.allow`; a new violation is fixed, or accepted in that file with a reason and a row in SPEC §12.10
- Error rules check (SPEC §14.4): `go run ./cmd/glutter-gen errcheck -allow cmd/glutter-gen/errcheck.allow`; a new violation is fixed, or accepted in that file with a reason
- Pointer rule check (SPEC §25.2, from step 28.19): `go run ./cmd/glutter-gen uintptrcheck -allow cmd/glutter-gen/uintptrcheck.allow`: in the Windows code a Go pointer becomes a `uintptr` only in the arguments of a `//go:uintptrescapes` or `SyscallN` call (a stack move or the GC would make it stale); a new violation is fixed, or accepted in that file with a reason
- Run an example: `go run ./examples/counter`; SVG pictures: `go run ./examples/svg`
- After changing dependencies: `go mod tidy`

## Definition of done
Before reporting a task as finished, run `gofmt`, `go vet ./...`, `golangci-lint run`, `go test -race ./...` and `go test -race -tags debug_mode ./...` (the tests in both modes), and fix anything they report. Say so explicitly if any step was skipped or failed. Also:
- `CGO_ENABLED=0 go build ./...` and `CGO_ENABLED=0 go test ./...` pass (proves the library stays cgo-free)
- From step 24.1 on: `go run ./cmd/glutter-gen errcheck -allow cmd/glutter-gen/errcheck.allow` passes (the error rules of SPEC §14.4)
- From step 19.1 on: `GOOS=js GOARCH=wasm go build ./...`, `GOOS=js GOARCH=wasm go vet ./...`, `scripts/test-wasm.sh` and `scripts/test-wasm.sh -tags debug_mode` pass
- From step 25.1 on: `scripts/check-android.sh` passes
- From step 28.1 on: `GOOS=windows GOARCH=amd64 go build ./...` and `go vet ./...`, `GOOS=windows GOARCH=arm64 go build ./...`, and `scripts/test-windows.sh` and `scripts/test-windows.sh -tags debug_mode` pass
- From step 28.19 on: `go run ./cmd/glutter-gen uintptrcheck -allow cmd/glutter-gen/uintptrcheck.allow` passes
- From step 28.15 on: `GOOS=windows golangci-lint run` (amd64 and arm64, with and without `--build-tags glutter_wine`) is clean
- Every new exported identifier has a doc comment that ends with its Flutter counterpart (see "Porting from Flutter")
- Every changed golden image has been looked at, not just regenerated

## Layout
- Public packages at the repo root mirror Flutter's libraries: `foundation`, `scheduler`, `animation`, `physics`, `gestures`, `painting`, `rendering`, `semantics`, `services`, `widgets`, `material`
- `gpu/` is the public GPU API of 1.10 (SPEC §27.2): the device of the renderer (`DeviceOf`, `OnDevice`), `gpu.View` (a widget with a render target of its size; step 30.6), buffers, textures, samplers, shader modules, pipelines, bind groups, command encoders and the queue; `gpu/shader.go` is the type of the shaders that `glutter-gen gpushaders` makes. It reaches the engine only through `ui.PlatformDispatcher.HostAs` and `internal/gpu/explicit.DeviceHost`. It names no OS or GPU-API type; its doc comments end with `// Flutter: no counterpart`. `internal/gpuhost` is the device host of its tests (`gluttertest`'s recording device, the display and browser tests); tests only
- `vecmath/` is the 3D math (SPEC §27.7: vectors, quaternions, matrices, rays, planes, boxes, frustums in float64, reversed-Z projections; its doc comments end with `// Flutter: package:vector_math ...` or `// Flutter: no counterpart`). `viewport3d/` is the 3D view (SPEC §27.8: `Scene`, `Item`, `Mesh`, the materials, `Camera` and its navigation, display modes with edges, section planes with caps, picking and selection, the grid, the axes, the view cube, `Anchored` widgets, `Renderer` for a view of your own, and `Upload`, which makes a scene of a `model.Model`; step 31.9 added `PBRMaterial` with image-based lighting (`Environment`, made by compute passes in `ibl.go`), one shadow map (`shadow.go`), tone mapping into `RGBA16Float` (`tonemap.go`), skins and morph targets (`skin.go`, storage buffers), and `Animation` with `Pose` (`animation.go`; step 31.11 added `Uploaded.SetTransform`, which moves a whole uploaded model: the character of a game); the PBR draw path is `pbrdraw.go`); it is plain Go over `gpu` and its shaders are generated (`go generate ./viewport3d`). A compute shader never turns a thread id into a float directly (`f32(i32(id.x))`: Wine's `d3dcompiler_47` gets `f32(id.x)` wrong, SPEC §9.8), and never reads a cube with the linear filter (SwiftShader on Android gets it wrong, SPEC §28.5). `model/` is the plain-Go data of a 3D model (SPEC §27.9, §28.5: meshes, materials with textures and the PBR parts, nodes with `TRS`, skins, morph targets, animations as data, cameras, lights, scenes), with the loaders `model/stl`, `model/obj`, `model/gltf`, `model/ply` and `model/threemf` (step 31.8: `.gltf` and `.glb`, accessors with strides, sparse and normalized values, the extensions of SPEC §28.5; every error is `GLTFInvalid` with a JSON-pointer `path` and a `reason`, or `GLTFExtensionUnsupported`; `testdata/sample-assets` has CC0 models of the Khronos Group with their license) (no GPU, no window; step 31.10 added `model/ply`: ASCII and both binary orders, point clouds with colors, polygons cut by `model/internal/poly`, positions in float64 when a file's doubles need it; and `model/threemf`: the model part found through the package's relationships, units, components with transforms, base materials and color groups, `Options.MaxModelBytes` against a zip bomb, the production extension not read; the errors are `PLYInvalid` and `ThreeMFInvalid` with a `reason`; a cloud's colors are `PointMaterial` `VertexColors`, entry `vs_color`). `internal/meshopt` is the decoder of `EXT_meshopt_compression` (vertex and index buffers, index sequences, the four vertex filters; plain Go ported from meshoptimizer 1.3, MIT, `third_party/meshoptimizer/LICENSE`, source in `reference/meshoptimizer`, fetched by `scripts/fetch-reference.sh`; each ported file says so). `internal/scenetest` has the scenes of the display tests and of the benchmarks of `viewport3d` (tests and benchmarks import it; no program does; `testdata/samples` has the CC0 glTF models of the PBR scenes, with their license)
- `gamepad/` is the gamepad package (SPEC §28.2: `Of(bc)`, `Gamepads` with `Pads` and `AppendPads` (a frame of a game appends to a slice of its own and allocates nothing), `AddMappings` and `SetKeyEvents`, `Pad` with its state, listeners, rumble and light, the buttons and axes of the standard layout, `ApplyDeadZone`); a thin face over `internal/pads` (the manager of the app, which the engine starts, so that pads make key events whether or not the app imports `gamepad`) and `internal/gamepaddb` (SDL 3's mapping format, table, GUID and pad kinds, and the layers that turn raw reports into the layout; plain Go, no OS tags; `mappings_gen.go` and `controllers_gen.go` come from `glutter-gen gamepaddb` and `reference/sdl`). `internal/gamepadhid` holds the HID drivers (SPEC §28.2, step 31.3: PlayStation 4 and 5, Switch Pro, Xbox One and Series over Bluetooth; plain Go over a `Transport`, `Device`, `Bridge`; `internal/platform/linux/evdev/{hidraw,hid}_linux.go` and `internal/platform/windows/{win32/hidfile_windows.go,winpad/drivers.go}` are their backends; ported from SDL's `hidapi` drivers, so the SDL-name rule applies); `internal/platform.Gamepads` is the interface of a platform's backend (raw pads and raw reports); `internal/platform/linux/evdev` is the Linux one (plain Go over `syscall`: sysfs probe, `epoll`, inotify, evdev, force feedback; the decoding and the numbering are in files with no OS tag, so tables of events test them anywhere); `internal/platform/windows/winpad` is the Windows one without a call into Windows (XInput and Raw Input HID pads behind two interfaces, tested on any host; `gamepads_windows.go` of package `windows` has the real calls and the message-only window), `internal/platform/web` has the browser's (`gamepads.go`, plain Go, and `gamepads_js.go`; `padtest` is the browser test's app), `internal/platform/android` the phone's (`gamepads.go`, with the Java `GamepadInput`), and `internal/platform/padstd` is what the backends of pads that report the standard layout share; `internal/platform/fake` and `gluttertest` (`ConnectPad`) script pads. Code ported from SDL 3 names its source file in a comment and no identifier of the module uses SDL's names (`glutter-gen apicheck` has the rule `sdl-name`, SPEC §28.1)
- `audio/` is the audio package (SPEC §28.3, step 31.4: `Of(bc)`, `System`, `Device`, `Stream`, the formats and states; Flutter has none) and `audio/wav` reads WAV files; the conversion and mixing are `internal/audiocvt` (plain Go ported from SDL 3's `src/audio`, with `channels_gen.go` from `glutter-gen audiochannels` and `reference/sdl`: sample types, the SDL channel layouts, the resampler, `Converter`, mixing), the platform side is `internal/platform.Audio` (`Services.Audio()`; Linux's is `internal/platform/linux/audio.go`, which asks `internal/platform/linux/pulse` (libpulse through purego: the threaded main loop, streams, subscription) and then `internal/platform/linux/alsa` (`snd_pcm_*`, a goroutine for each device), step 31.5; `internal/platform/windows/wasapi` is WASAPI (plain Go for the formats, COM through `win32`, a thread of its own for each device), `internal/platform/android/aaudio` is AAudio through purego (it has the `linux` tag so that its unit tests run on the host over a scripted library; `internal/platform/android/audio*.go` wire it to the lifecycle and to the `RECORD_AUDIO` question that the Java `AudioPermission` asks), and `internal/platform/web/audio*.go` with `internal/webtool/audio_worklet.js` (which `glutter-web build` writes as `glutter-audio-worklet.js`) is Web Audio; step 31.6) and `internal/platform/fake` has the scripted device that `gluttertest.Tester.Audio()` shows; the SDL-name rule applies
- `sensors/` is the motion sensors package (SPEC §28.4, step 31.7: `Of(bc)`, `System`, `Sensor`, `Reading`, `Kind`, `Feed`; Flutter has none in its framework; its doc comments end with `// Flutter: no counterpart`); the platform side is `internal/platform.Sensors` (`Services.Sensors()`, `SensorsHost`; Android's is `internal/platform/android/asensor`, the sensor manager of libandroid through purego with a looper on a locked goroutine, a package with the `linux` tag so that its tests run on the host over a scripted library, ported from SDL 3's `src/sensor/android`, so the SDL-name rule applies; the web's is `internal/platform/web/sensors{,_js}.go`, which also has `HapticMillis` for `navigator.vibrate`; the Linux and Windows desktops have none: a pad's sensors reach `sensors.Sensor` through `gamepad.Pad.OpenSensor` and `sensors.Feed`); `internal/platform/fake` and `gluttertest` (`Tester.Sensors()`, `PadSpec.Sensors`, `TestPad.Sensor`) script them
- `ui/` is the engine API (Flutter's `dart:ui`): geometry, Canvas, Paint, Path, Scene, Paragraph, views, input events
- `desktop/` holds desktop services Flutter leaves to plugins: system tray, notifications, file dialogs, open-URI
- `gluttertest/` is the widget-testing package (Flutter's `flutter_test`)
- `internal/platform/` holds the platform interface and its backends (`linux/wayland`, `linux/x11`, `web`, `android`, `windows`, `fake`); `linux/dl` loads C libraries through purego, and `linux/dl/layouttest` holds the struct-layout test helper (it imports `testing`, so only tests import it; `examples/no_testing_test.go` checks that no program links `testing`); `windows/win32` is the package that calls Windows (DLLs, COM, callbacks, the struct mirrors and their `layouttest`), and `windows/ole` holds the COM objects Go makes for OLE drag and drop and their plain-Go models; `windows/uia` is the UI Automation bridge (plain-Go model, COM providers, and the test helpers `callshim`, `semtree` and `uiatest`)
- `internal/gpu/` holds the renderer interface and its backends (`vulkan`, `gles`, `soft`, `webgpu`, `canvas2d`, `nativewindow`, `gdiwindow`, `shmwindow` (`soft` into the shared memory of a Linux window, through `gpu.PixelTarget`: `wl_shm` on Wayland, MIT-SHM or `XPutImage` on X11, with the buffer pool of `internal/platform/linux/pixelpool`; steps 32.1 and 32.2), `d3d12`: the Direct3D 12 `explicit.Device` and its HLSL compiler), and `shadercache` keeps what they compile between runs; `explicit` is the renderer that `vulkan` and `webgpu` share, with its WGSL shaders
- `internal/winetest/` is the Wine harness; `.wine-test/` (git-ignored) holds its prefix
- `internal/text/` holds paragraph layout on go-text, with `androidfonts` and `winfonts` (the plain-Go matchers of the Android and Windows system fonts) and `fonttest` (test fonts made from the bundled fonts with another `cmap`); `internal/dbus/` holds the D-Bus services
- `internal/leaktest/` is the memory-test harness (tests only: it imports `testing`, so no program may link it); `internal/platform/linux/dl` also counts C blocks (`LiveBlocks`, `TrackBlocks`) and the C heap (`CHeapInUse`)
- `internal/svg/` is the SVG parser and painter (SPEC §26, D27; plain Go, standard library only, no OS tags); `svg/` is the public package with `flutter_svg`'s widgets (`SvgPicture`, `Cache`, `SvgTheme`); `material` does not re-export it, and its doc comments end with `// flutter_svg: <file> <Name>`, which `apicheck` accepts. Doc comments in `internal/svg` cite `// SVG 1.1: <section>` or `// SVG 2: <section>` instead of "Flutter:". `reference/flutter_svg` (git-ignored, from `scripts/fetch-reference.sh`) is for the API names of package `svg` only
- `offscreen/` is the public package that draws off screen (SPEC §9.9, D28): a software `ui.Rasterizer`, a `Detacher` that makes a scene safe to draw on any goroutine, a `Surface` that keeps the pixels of a view and redraws only what changed, and `NewView`, a widget tree in a view on a binding of its own that draws on a goroutine of its own. It is plain Go over `internal/gpu/soft`, with no OS tags; its doc comments end with `// Flutter: no counterpart`
- `cmd/glutter-gen/` holds the code generators; `cmd/glutter-web/` builds, serves and screenshots apps for the web; `cmd/glutter-android/` builds, installs, runs and screenshots apps on Android, with `internal/androidtool` (packaging, the Java embedding and its checked-in `classes.dex`) and `internal/androidtest` (the emulator harness); `cmd/glutter-windows/` builds, runs, screenshots and measures (`perf`) apps for Windows, with `internal/wintool` (the manifest, the pure-Go `.syso` writer, the icon and version resources, the build in a temporary copy, the Wine launchers); `examples/<app>/` holds runnable examples (public API only; `examples/game3d` is Coin Run, the games example of step 31.11: its rules are in `world.go`, plain Go with no window, and its glTF and WAV files in `assets/` are made from numbers by `internal/genassets`, run by `go generate ./examples/game3d`; the tests of the memory and the speed of its level are in `viewport3d`, `gamepad` and `audio`), and `examples/dev/<app>/` holds early development examples that may use `internal/`; `scripts/` holds helper scripts
- `docs/IMPLEMENTATION.md` is the step-by-step plan; `docs/IMPLEMENTED.md` logs finished steps; `docs/implemented-proof-images/` holds each step's proof screenshots
- `reference/` (git-ignored) holds the pinned Flutter sources used for porting (SPEC §20). Never import, vendor or commit it
- Tests live next to the code (`foo_test.go`); golden images live in `testdata/goldens/` of their package

## Go conventions
- Never ignore a returned error; handle it or return it
- Pass `context.Context` as the first parameter of anything that does I/O (assets, images, fonts, D-Bus, file dialogs). Name it `ctx`. Name a `BuildContext` `bc`
- Tests are table-driven
- No global mutable state. In particular, no singletons like Flutter's `WidgetsBinding.instance`: code reaches the binding through `BuildContext` or constructors. Package-level read-only values (`Colors`, `Icons`, `Curves`) are fine and are never reassigned. The only process-wide mutable state is what Windows or Wine forces, each with its reason in the file: `ole.Shared` (COM callbacks are never freed) and the COM worker threads of `internal/platform/windows/worker_windows.go` (Wine never forgets an apartment's RPC endpoint)
- Prefer the standard library. Allowed dependencies: `github.com/rm4n0s/errors`, `github.com/go-text/typesetting`, `golang.org/x/image`, `github.com/godbus/dbus/v5` and `github.com/ebitengine/purego`. Ask before adding any other
- **No cgo**: never write `import "C"`, except in the `*_android.go` files of `internal/platform/android` (JNI and the NDK, D21; SPEC §24.2). C libraries are otherwise called only through purego, and only under `internal/platform/<os>/...`, `internal/gpu/gles`, `internal/gpu/vulkan` and `internal/gpu/nativewindow`. `GOOS=android` satisfies the `linux` tag: a file only for the Linux desktop says `linux && !android`. OS build tags are allowed only there, in `internal/dbus`, `internal/platform/web`, `internal/webtest` (the process group of the browsers it starts), `internal/gpu/webgpu`, `internal/gpu/canvas2d`, the `backends_<goos>.go` files and `gles_renderer.go` (`linux || js`) of `internal/engine`, `internal/androidtest` (the emulator's process group), `foundation/web_*.go` and `foundation/host_android.go` (SPEC §6.3). C memory, Go mirrors of C structs and function pointers never cross those package boundaries
- **Windows** is called only through the standard library's `syscall` (`SyscallN`, `NewCallback`), never purego and never `golang.org/x/sys/windows` (not an allowed dependency), and only in `internal/platform/windows/...`, `internal/gpu/d3d12`, `internal/gpu/gdiwindow` and the Windows files of `internal/engine`. The `windows` build tag is allowed there, in `internal/winetest` (with `linux` for the side that starts Wine), `internal/engine/backends_windows.go`, `foundation/host_windows.go` and `cmd/glutter-windows`. `GOOS=windows` satisfies neither `linux` nor `unix`. The Go mirrors of Win32 and COM structures live in files with no OS tag and each has a `layouttest` against the mingw-w64 headers (skipped without `mingw64-gcc`). Callbacks are made once, as with purego (SPEC §6.3 rules 10–11, §25.2). Go assembly is allowed only for the COM thunks that take floating-point arguments, in `internal/platform/windows/uia` and `uia/callshim` (`*_windows_amd64.s`, `*_windows_arm64.s`; SPEC §25.2), and for `internal/goid`'s one function that reads a word of the running goroutine's `g` (`gword` in `getg_amd64.s`, `getg_arm64.s`: the goroutine's number, at an offset found at run time, never the `g`'s address, which the runtime reuses; the owner's choice of 2026-10-28; SPEC §6.3 rule 13, §13). Under Wine, a UI Automation client never subscribes to `Text_TextChanged` or `LiveRegionChanged`: Wine 11 then blocks the thread that raises the event
- `syscall/js` is imported only in `internal/platform/web`, `internal/gpu/webgpu`, `internal/gpu/canvas2d` and the WebGL 2 files of `internal/gpu/gles`. Once the event listeners are installed, the UI goroutine never waits for a JavaScript promise (SPEC §23.3)
- purego rules (SPEC §8.1):
  - never call a C variadic function; use the non-variadic variant (e.g. `wl_proxy_marshal_array_flags`)
  - create C→Go callbacks once at startup (a process can have ~2,000) and dispatch by user data
  - every Go mirror of a C struct has a layout test
  - data C keeps lives in C memory
- No `runtime.GOOS` checks in the framework. Platform-dependent behavior goes through `foundation.TargetPlatform`, like Flutter's `defaultTargetPlatform`
- Only the UI thread touches the framework, GL or the display connection. Other goroutines hand work over through `SetState` or the binding's `Post` (SPEC §13)

## Flutter API conventions (summary of SPEC §12)
- Every widget and public class is created by a constructor `NewX(required..., opts ...XOpts) *X`
  - Flutter's `required` parameters become positional arguments, so the compiler enforces them
  - Optional parameters go in a trailing options struct; passing more than one options value panics
- Positional order follows Flutter's declaration order, except `child`/`children` always come last. A required-but-nullable parameter (e.g. `onPressed`) is still positional, and `nil` means what `null` means in Flutter
- Named constructors become `NewXName` (`ListView.builder` → `NewListViewBuilder`); static methods become `XName` functions (`Theme.of` → `ThemeOf`, `Navigator.push` → `NavigatorPush`)
- Names, defaults and semantics follow Flutter. In options structs, a nullable Flutter parameter whose `null` differs from Go's zero value becomes `foundation.Opt[T]` (`m.Some(v)`). An enum's zero value is `<Enum>Unspecified`, meaning "the widget's default"
- `material` re-exports everything in `widgets` through generated wrappers, so apps import one package

## Error handling
Use `github.com/rm4n0s/errors` (v0.2.0) for all errors, the way its `AI_GUIDE.md` says. This is a requirement of the project owner: read the whole guide (it is in the module cache, `$(go env GOMODCACHE)/github.com/rm4n0s/errors@v0.2.0/AI_GUIDE.md`) before you write or change code that makes, returns, logs or tests an error, and again when the dependency version changes. SPEC §14.4 lists the rules with the reasons, and `go run ./cmd/glutter-gen errcheck -allow cmd/glutter-gen/errcheck.allow` checks them. Never use `fmt.Errorf`, and never import the standard library `errors` package under the name `errors`: this package re-exports `errors.Is`, `errors.As` and `errors.Unwrap`, so a single import covers everything (if `Join` is needed, import the standard one as `stdErrors "errors"`).

**Creating errors**
- New failure with a fixed message: `errors.New("Tag", "message", "key", value, ...)`. It always has a tag and a message
  - Tag: short PascalCase name of the thing the function cannot do, e.g. `WaylandConnectFailed`. Declare it as a constant next to the code that produces it (`const tagWaylandConnectFailed = "WaylandConnectFailed"` at the end of the file; exported as `TagX`, with a doc comment, when another package matches on it)
  - Trailing arguments are key/value metadata pairs with string keys, e.g. `"display", name`. Give all of them in this one call; never chain `SetMetadata` after `errors.New`
- New failure with a formatted message: `errors.NewErrf("Tag", "format %s", arg)`
- Wrapping an error that comes from outside this module (stdlib, C library error codes, godbus, go-text, any third-party package): `errors.NewErr("Tag", err)`, once, where it first appears. `NewErr` and `NewErrf` take no metadata: add it with one `.SetMetadata("key", value, "key2", value2)` call. `SetMetadata` merges, so a later call in another function adds keys; `RemoveMetadata` and `SetMessage` change an error that is already made. `NewErr(tag, nil)` panics, so call it only inside `if err != nil`
- Call the constructor in the function that fails, never in a helper that builds and returns the error: the route is the call stack at the constructor, and a helper adds a frame that is not the failing function. (The one exception is a table that turns a C error code into a tag with a switch, such as `vkError`, listed in `errcheck.allow`; an exported function or method is not a helper)
- Every `New`, `NewErr` and `NewErrf` call captures the stack at that point
- A sentinel for `errors.Is` is a struct literal, `&errors.Error{Tag: TagX}`. Never write `var ErrX = errors.New(...)` at package level: its route is `init`

**Propagating errors**
- Every error is tagged exactly once. If the error came from a function of this module, return it untouched: `return err`. Re-wrapping it (`NewErr`, `NewErrf` with `%w`, `fmt.Errorf`) would replace the Tag and the stack and break route tests; the route already shows who called whom, so no context is added by wrapping
- Functions return the plain `error` interface, never `*errors.Error` (avoids the non-nil-interface-holding-nil-pointer bug)
- `errors.FromError(err)` is a plain type assertion. It fails if something else wrapped the error, so don't wrap these errors with anything

**Inspecting errors**
- `appErr, ok := errors.FromError(err)`, then use `appErr.Tag`, `appErr.Metadata`, `appErr.Message`
- Branch on the tag constant (`appErr.Tag == pkg.TagX`) or on `errors.Is(err, sentinel)` (it matches by Tag), never on a string literal, `Message` or `Error()`
- Use `errors.Is` / `errors.As` / `errors.Unwrap` for the underlying cause stored in `OriginalErr`

**Logging errors**
- Log with `slog` and pass the error as the attribute `"err"`: `logger.Error("what failed", "err", err)`. `*errors.Error` is an `slog.LogValuer`: the entry has `Tag`, `Message`, `Route`, `OriginalErr`, `Metadata` and `StackFrames`, and a test replays it with `json.Unmarshal` into `errors.ErrorJson` and `errors.FromJson`. Do not call `ToJson` or `json.Marshal` on an error to log it
- Metadata values must be JSON-serializable (strings, numbers, bools, simple structs); after a round trip numbers are `float64`

**Testing errors**
- Every new failure case gets its own unique Tag and a test that asserts the route, not just that an error occurred:
  ```go
  appErr, ok := errors.FromError(err)
  if !ok {
      t.Fatalf("expected *errors.Error, got %T", err)
  }
  if !appErr.HasRoute("Engine.Start->Wayland.Connect.WaylandConnectFailed") {
      t.Errorf("unexpected failure path: %s", appErr.Route())
  }
  ```
- A route lists the call chain from outermost to innermost (`Type.Method` or `Func`, joined by `->`, no package names) and ends with the Tag. `Route` and `HasRoute` stop at the function that called them, so in a test the route starts just below the test function. `HasRoute` matches by substring: give the path from the entry function you call down to `.Tag`, so the tag is checked too. Print `appErr.Route()` when an assertion fails
- Panics in user code and programmer errors follow SPEC §14

## Testing notes
- Widget tests use `gluttertest` (`PumpWidget`, `Pump`, `Tap`, finders) with a fake clock and the fake platform; no display needed
- Golden tests render through the software renderer (`internal/gpu/soft`), so they are deterministic and need no GPU
- Tests that open real windows or GL contexts carry the `glutter_display` build tag and are skipped by the default test run. Vulkan display tests use Mesa's lavapipe with validation on (SPEC §17)
- Tests that run in a headless browser carry the `glutter_browser` build tag; they use `internal/webtest` and temporary browser profiles
- Tests that need an audio server carry the `glutter_audio` build tag and run under `scripts/headless-audio.sh`; they skip without it
- Tests that run on the Android emulator carry the `glutter_android` build tag; they use `internal/androidtest`. What only a real phone shows is a manual check (SPEC §24.13)
- Tests that run inside Wine carry the `glutter_wine` build tag; `scripts/test-windows.sh` runs the unit tests of the packages that build for Windows under Wine
- A test that opens Windows windows keeps one OS thread from `New` to `Close` (`runtime.LockOSThread`). The Wine prefix gets copies of the host's Liberation Sans in `C:\windows\Fonts` (`scripts/wine-exec.sh`); some Wine tests are host-side (`go test -tags 'glutter_wine debug_mode' -p 1 ./internal/winetest ./cmd/glutter-windows ./internal/platform/windows ./examples/counter ./examples/scrolling ./examples/editor`): they start Wine themselves. The Wine clipboard tests start the test binary a second time as the other program (`TestWineClipboardHelper`); the settings tests write into the private prefix's registry and remove what they wrote. A pixel test never ends on a blinking caret (end the script with a selection), and a scripted key that works on the laid-out value waits for a frame after the edit before it. Under Wine `auto` draws with `d3d12`: a Wine test that compares frames pixel for pixel runs with `GLUTTER_RENDERER=soft` or `GLUTTER_RASTER_CACHE=0`, and one that compares `d3d12` with `soft` uses `gputest.Tolerance`. The tray Wine tests run in a child process on Wine's `explorer /desktop=glutter,800x600` (`TestWineShellServices`): threads of one process must not be on two Wine desktops. The `internal/gpu/d3d12` Wine suite takes 3 to 4 minutes and about 3 GB (vkd3d takes about 120 MB for each shader-visible descriptor heap): run it alone
- Every error Tag has a route test
- A memory test calls `Tester.ClearLogs` and uses `DiscardScenes`, so that the logs of the fakes are not counted as the app's memory. A state keyed by a pointer or a view is deleted when the pointer or view ends (every press has a new id)
